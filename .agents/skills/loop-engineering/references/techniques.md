## 1. ループエンジニアリングの本質
ループエンジニアリングとは、「人間が毎回手動でプロンプトを入力してAIを制御する」のではなく、**「AIが過去のセッションログ（JSONL等の履歴）から自己の課題や学びを自律的に分析し、ルール（ハーネス）を自動更新して次のセッションに適用する仕組み」**のことです。

このサイクルを回すことで、開発・業務を進めれば進めるほど、AIがあなた好みの動き、チームの仕様、プロジェクトの暗黙知にフィットするように「勝手に育って」いきます。

## 2. 6つの実践テクニック詳細

### テクニック①：1行プロンプトによる `claude.md` 改善
もっともシンプルで、今日から1秒で始められる基本形です。過去のセッション履歴をAI自身に探索させ、人間が毎回イライラしているポイント（癖、仕様の解釈違い、同じ説明の繰り返し）を自動で抽出します。

#### ■ 準備するファイル
*   `claude.md`（または `system_prompt` など、AIがセッション開始時に必ず読み込むシステム指示ファイル）
*   **セッションログ（JSONL）**: あなたの開発プロジェクトに蓄積されているやり取りの履歴。

#### ■ 実践プロンプト
セッション中に以下のプロンプトをそのままAI（Claude Codeなど）に実行します。

```text
このプロジェクトの JSONL 履歴を検索して今の claude.md の改善点を分析して、私がイついている箇所と、セッションをまたいで同じことを聞いているパターンを挙げて。
```

#### ■ 運用プロセス
1.  **分析実行**: 上記プロンプトを週に1回程度実行し、AIに「人間のストレスポイント」を自己分析させます。
2.  **ルール更新**: AIが提示した改善案を承認し、`claude.md` のルール（「必ずファイルの存在を確認してから書くこと」など）に反映させます。
3.  **自律的成長**: 新しいセッションからは、更新された `claude.md` に基づいて動くため、過去と同じミスやイライラが発生しなくなります。

### テクニック②：`learnings.md`（ラーニングMD）自己学習ループ
セッションの開始時と終了時に「学びのロード＆セーブ」を完全に自動化し、セッションをまたいだ知見の蓄積をシステム化するテクニックです。

#### ■ 準備するファイル
*   `learnings.md`：AIが獲得した暗黙知や業務ルール、失敗防止策を蓄積する専用ファイル。
*   `claude.md`（システムルール）：開始・終了時にこの処理を実行するよう定義。

#### ■ `claude.md` に組み込むシステム指示

```markdown
# ラーニングMDループ（自己学習サイクル）

## セッション開始時の指示
- 各セッションの開始時に、必ず `/workspace/learnings.md` を読み込むこと。
- 読み込んだ内容を簡潔に要約し、適用済み（コンテキストに展開完了）であることがユーザーに伝わるように報告すること。

## セッション終了時（フック処理）
- セッションの終了、または大きなタスクの完了時に、必ず `/workspace/learnings.md` をアップデートすること。
- このセッションの作業を振り返り、以下の「4つの観点」から新しい学びや修正点を洗い出せ。
  1. うまくいったアプローチ（ベストプラクティス）
  2. 発生した失敗と、その再発防止策
  3. 獲得したドメイン知識（業務・仕様のルール）
  4. 次回以降も覚えておく価値のある調整事項
- 洗い出した内容を `/workspace/learnings.md` の該当セクションに簡潔な項目（箇条書き）として追記・更新せよ。
```

#### ■ 定期的な「原則化（マージ）」プロセス
情報のノイズや重複が増えるのを防ぐため、週に1回、以下のプロンプトを投げて `learnings.md` を綺麗に整理（原則化：Consolidated Principles）します。

```text
`/workspace/learnings.md` を開き、全体を見直して。
1. 古くなった項目や、すでに現在の開発仕様と矛盾しているものを削除。
2. 重複している内容をマージ。
3. 共通のパターンを見つけ出し、より抽象度の高い「行動原則（Consolidated Principles）」に統合してまとめ直して。
```

### テクニック③：自律型AI番人「タスクオブザーバー」
自律的に動く監視役（オブザーバー・スキル）を作り、メインの作業を邪魔することなく、スキルの欠陥や新しい最適化の芽（キャンディ）をステージングエリア（バッファ）に収集・育成する高度なテクニックです。

#### ■ 準備するファイル
*   `skill_observation_log.md`：タスクオブザーバーが記録する監視ログ。
*   `skill_updates/`：直接既存の指示ファイルを上書きせず、一時的に修正案を保存（ステージング）するディレクトリ。

#### ■ `claude.md` に組み込むシステム指示

```markdown
# タスクオブザーバーの有効化
- 作業（タスク）が3件完了する、または一定の作業フェーズが終わるたびに、バックグラウンドで「タスクオブザーバー（Task Observer）」を呼び出せ。
- タスクオブザーバーは、このセッションのログを観察し、次の3点のみを観察ログ `/workspace/skill_observation_log.md` に追記せよ。
  1. 【抜け落ちていたルール】：ユーザーの「修正指示」によって初めて露呈した、本来定義しておくべきだった前提ルール
  2. 【スキルのギャップ】：既存のシステムプロンプトやスキルが、現在の状況や仕様をカバーできていなかった部分
  3. 【有効だったテクニック】：そのセッションで作業効率を大きく上げた、またはブレイクスルーにつながった具体的なアプローチ
- 観察結果に基づく既存ルールの「修正案」は、ルール本体を直接書き換えるのではなく、`/workspace/skill_updates/` に一時保存（ステージング）せよ。
```

#### ■ ログの記録形式（蓄積イメージ）
```markdown
# skill_observation_log.md

## 2026-09-08 [仕様書作成タスク]
- **抜け落ちていたルール（Existing Skill Gap）**: Codebaseの実装を読み込まずに、憶測だけでドキュメントの記述を進めてしまい、ユーザーから手戻りの指摘を受けた。
  - *改善原則*: 出力の根拠となるソースコードが存在する場合、文章作成前に必ず対象ファイルを読み込ませるルールを「仕様作成スキル」に追加すべき。
- **新規スキルの候補（New Skill Candy）**: ローカルのAPIモックサーバーを1コマンドで立ち上げつつテストを実行する手順が、手動の切り替え作業を大幅に削減した。
  - *新規スキル候補*: 「ローカル環境高速検証自動化スキル」として定義可能。
```

### テクニック④：蓄積したログから一括課題抽出「ログマイニング」
すでに過去の開発ログ（JSONL）が大量にたまっている場合、1本ずつ人間がチェックするのは不可能です。サブエージェントを擬似的に並列稼働させ、横断的にログをスキャンして「システムの最大のボトルネック」を一気に抽出します。

#### ■ 実践プロンプト
```text
このプロジェクトのセッションログ（JSONLなど）をファイルサイズが大きい順に100本並べて。
それを10本ずつグループに分け、サブエージェント10体で並列に読み込ませて分析するシミュレーションを実行して。

各サブエージェントは、担当する10本について次の3点「のみ」を報告すること：
1. 実データ（コードやログ）を確認せずに、憶測で回答・進行して手戻りが発生した箇所
2. ファイルの場所を探すためだけに、検索系ツールの呼び出しを何度も浪費した箇所
3. 過去のやり取りで一度発見したはずの知識を、別のセッションで「再発見」していた箇所

最後に、これら10グループの分析結果を統合し、上記の課題が「全何グループで出現したか」が多い順にランキングにして、具体的なボトルネックとなっている箇所を解説して。
```

### テクニック⑤：定性プロセスデータ分析（ビジネス・営業への応用）
開発だけでなく、営業の顧客対応履歴やコールセンターの対話ログ、CRMの活動ログなど「雑多な定性データ」を分析し、**システム的に自動検証可能な「定量ルール（アラート条件）」**へと変換するアプローチです。

#### ■ 分析の入力データ
*   成約した商談150件、失中（失注）した商談150件の雑多なテキストログ（CRMの商談メモ、活動履歴、メールのやり取り数、通話書き起こしの要約など）。

#### ■ 実践プロンプト（6つの分析軸）
```text
提供した商談データ（成約・失中含む）を読み込み、以下の「6つの軸」に厳密に絞って横断分析を行って。

【分析の6軸】
1. タイミング（初回連絡からデモ、クローズまでの日数推移）
2. ステークホルダー（顧客側で会話に参加した役職者・意思決定者の人数や関与度）
3. 活動量（メールの往復回数、ミーティングの頻度）
4. 競合（競合他社の名前が出現したタイミングや頻度）
5. 反論（顧客から出たボトルネック、価格や機能への懸念）
6. メッセージ（顧客に響いた、または響かなかった訴求ポイント）

分析の結果として、成約した商談と失中した商談における「定量的・統計的な違い（平均日数、平均ステークホルダー数、メール数、競合出現率など）」を算出し、比較テーブルで出力して。
```

#### ■ 分析結果から「自動検証可能なルール」への落とし込み例
AIの分析によって「成約時は意思決定者が平均2.8人登場するが、失中時は1人」「45日を超えた商談は失中率が急上昇する」「最終盤の通話で競合名が出ると43%が失中する」といったデータ（特徴）が判明した場合、以下のように**「業務の監視ループを回すためのシステムルール」**へと昇華させます。

```markdown
# 営業管理システムの自動アラート・検証ルール
- **期間アラート**: 初回デモから「45日」を経過してもクローズの目処が立たない商談は、自動的に「停滞リスク（黄信号）」として営業担当者に警告を出す。
- **コンタクト警告**: ステークホルダーの登録数が「1名」のまま2週間以上経過している場合、役職者へのアプローチを促す指示を出す。
- **エスカレーション・トリガー**: 商談最終フェーズのメール、または対話ログに「競合名」が出現した場合、即座にマネージャーへエスカレーションする。
```

### テクニック⑥：環境移行をスムーズにする「セッションID/パス」引き継ぎハック
AIのトークン枠制限（使用制限）に達してしまった場合や、別のより高速・強力なAI（Claude CodeからCursor、Codexなど）に途中のコンテキストを渡して作業を継続させたい場合に、セッション履歴そのものをコンテキスト（テキストファイル）としてパス渡しする裏技です。

#### ■ 手順1：稼働中のセッションでパスを確認する
作業が進行しているAIセッション内で、以下の質問をします。

```text
現在のセッションID、またはこの会話履歴のセッションログが保存されているファイルパスを教えて。
```
*(AIはローカル環境における自分の実行パスやJSONL等のログファイルの場所を教えてくれます。例：`/home/user/.claude/sessions/session_xxxx.jsonl` など)*

#### ■ 手順2：移行先の新しいAIセッションで引き継ぐ
枠が切れた後に立ち上げた別のAI（または Cursor など別ツール）のチャットに、以下のようにパスを渡して指示します。

```text
以下のセッションログファイルを読み込んで、途中からこのセッションの続きを再開したい。
これまでの文脈（実装したコード、確認した仕様、発生していたエラー）をすべて理解し、要約して。

【セッションログのパス】
[手順1で取得したファイルパス]
```

#### ■ メリット
*   履歴をすべて再送信したり、人間が「ここまでの状況を説明する」必要がなくなります。
*   AIに「セッションそのものをオブジェクト（コンテキスト）として扱わせる」ため、ノイズを省いて必要な情報のみを凝縮して別環境へ瞬時に同期させることができます。

## 3. 今日から実践するためのロードマップ

1.  **ステップ1**: 今日行う開発セッションの最後に、**テクニック①の1行プロンプト**を実行して `claude.md`（システムルール）を修正してみる。
2.  **ステップ2**: 開発フォルダ内に `learnings.md` を作成し、**テクニック②の自動ロード＆セーブ指示**を `claude.md` に追加してセッションを複数回またいでみる。
3.  **ステップ3**: 開発が高度化してきたら、**テクニック③のタスクオブザーバー**を起動させ、スキルを別ファイル（ログとステージング）で自律育成する仕組みに移行する。
